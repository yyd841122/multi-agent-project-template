# Acceptance Example

> **说明**：这是一个验收标准示例，展示如何制定清晰、可测试的验收标准。
> 本示例来自 todo-agent-workflow-demo 项目的简化版本。
> 请根据实际项目需求修改此模板。

---

## 1. 验收原则

### 1.1 核心原则

**Tester 必须独立验收**：
- 不能只看开发报告就 PASS
- 必须读取实际代码并逐项对照验收标准
- 开发报告说做了什么，要验证实际做了什么

**验收标准必须清晰**：
- ✅ 明确具体：不使用"美观"、"友好"等模糊词
- ✅ 可验证：可以通过测试检查
- ✅ 完整：覆盖任务的所有要求
- ✅ 可测试：Tester 可以据此进行验收

### 1.2 判定标准

**PASS 判定**：
- 所有验收标准测试通过
- 无严重问题
- 无一般性问题（或一般性问题可接受）
- 开发报告与实际实现一致
- 历史功能没有被破坏（重构任务）

**FAIL 判定**：
- 至少一项验收标准未通过
- 存在严重问题
- 开发报告与实际实现严重不符
- 历史功能被破坏（重构任务）
- 代码有明显错误

## 2. 示例验收标准

### 2.1 整体验收标准

**功能完整性**：
- ✅ 所有需求文档中列出的功能均已实现
- ✅ 所有功能正常工作，无明显 Bug
- ✅ 功能交互流畅，用户体验良好

**代码质量**：
- ✅ 代码结构清晰，易于理解
- ✅ 代码格式规范，缩进统一
- ✅ 变量和函数命名清晰
- ✅ 无明显的代码冗余
- ✅ 关键逻辑有适当注释

---

### 2.2 示例任务验收标准

#### T001: 创建项目基础文件结构

**验收步骤**:
1. 检查项目根目录是否存在基础代码文件
2. 在浏览器中打开主文件
3. 打开浏览器开发者工具，检查 Console 是否有错误

**通过标准**:
- ✅ 基础文件都存在
- ✅ 文件引用关系正确
- ✅ 页面打开无报错

---

#### T002: 实现基础页面结构

**验收步骤**:
1. 在浏览器中打开主页面
2. 检查页面元素
3. 使用开发者工具检查 HTML 结构

**通过标准**:
- ✅ 显示页面标题
- ✅ 有必要的输入区域
- ✅ 有输出/列表区域
- ✅ HTML 结构语义化
- ✅ 关键元素有 id 或 class

---

#### T003: 实现核心功能

**验收步骤**:
1. 测试核心功能的基本使用
2. 测试输入校验（如有）
3. 测试边界情况

**通过标准**:
- ✅ 核心功能可以正常使用
- ✅ 输入校验正常工作
- ✅ 基本交互流畅
- ✅ 没有明显的 Bug

---

#### T004: 编写项目文档

**验收步骤**:
1. 检查 README.md 是否存在
2. 阅读文档内容
3. 按照文档操作验证

**通过标准**:
- ✅ 文件存在
- ✅ 包含运行/打开说明
- ✅ 包含功能使用说明
- ✅ 文档清晰易懂

## 3. 回归验收要求

### 3.1 什么时候必须做回归验收

**必须做回归验收的情况**：
1. 重构类任务（代码重构、样式重构）
2. 修改核心逻辑的任务
3. 修改公共函数的任务
4. 修改数据结构的任务

### 3.2 回归验收要测什么

回归验收要检查：**历史功能是否被破坏**

**示例**：

假设 T005 是代码重构任务，Tester 必须检查：

1. **T001-T004 的所有功能是否正常**
   - 页面能否正常打开
   - 核心功能是否正常
   - 交互是否正常

2. **行为是否改变**
   - 用户输入行为是否保持一致
   - 如果行为被改变 → FAIL（行为被改变）

### 3.3 重构类任务的专项检查

**重构类任务必须重点检查历史功能是否被改变。**

**关键注意事项**：
- 对"用户输入"保持原值
- 不要擅自使用 trim()、toLowerCase() 等会改变原始值的方法
- trim() 只能用于空输入校验，不能改变最终保存的用户输入内容

## 4. FAIL 报告要求

当测试失败时，Tester 必须提供详细反馈。

### 4.1 FAIL 报告必须包含

1. **问题描述**
   - 哪项验收标准未通过
   - 具体问题是什么

2. **复现方式**
   - 如何操作才能复现问题
   - 详细的操作步骤

3. **影响范围**
   - 问题影响了什么功能
   - 是否影响其他功能

4. **建议修复方向**
   - 建议如何修复
   - 可以提供具体建议

### 4.2 FAIL 报告示例

```markdown
## 发现的问题

### 问题 1: 空输入校验不生效

**问题描述**:
验收标准要求"空输入不能添加内容"，但实际空输入时仍然可以添加。

**复现方式**:
1. 打开页面
2. 不输入任何内容
3. 点击"添加"按钮
4. 观察到空内容被添加到列表

**影响范围**:
- 影响数据质量
- 可能导致用户体验问题

**建议修复方向**:
建议在核心函数中添加空输入校验：
```javascript
if (input.value.trim() === '') {
    return; // 不添加空内容
}
```
```

## 5. 独立验收检查清单

Tester 在验收时，应该遵循以下检查清单：

### 5.1 验收前检查

- [ ] 读取了任务文档和验收标准
- [ ] 读取了开发报告
- [ ] 读取了 memory/lessons.md（了解有效经验）
- [ ] 读取了 memory/pitfalls.md（了解已知陷阱）

### 5.2 验收中检查

- [ ] 逐项对照验收标准
- [ ] 检查代码与开发报告是否一致
- [ ] 实际测试功能（不能只看代码）
- [ ] 检查历史功能是否被破坏（重构任务）
- [ ] 检查是否有超出范围的功能

### 5.3 验收后检查

- [ ] 判定结果明确（PASS 或 FAIL）
- [ ] FAIL 时提供了详细反馈
- [ ] 生成了完整的测试报告
- [ ] 记录了 TEST_ID

## 6. 重构任务特别注意事项

### 6.1 重构任务的核心原则

**只改代码结构，不改功能行为**

重构的目的是让代码更易读、易维护，而不是改变功能。

### 6.2 绝对禁止的行为

**重构时不得改变历史功能行为。**

**经典案例**（来自 todo-agent-workflow-demo Task 012）：
- ❌ 错误：将 `taskInput.value` 改为 `taskInput.value.trim()`
- ✅ 正确：`const taskText = taskInput.value;` 保留原始输入，`trim()` 只用于空输入校验判断

**为什么错误**：
- Task 012 重构时，Developer 无意中将用户输入的首尾空格丢弃
- 这改变了历史功能行为（Task 005 的原有设计是保留用户输入的原始内容）
- Tester 通过独立验收发现了这个问题

### 6.3 重构前必须做的事

1. **理解原有功能的完整行为**
2. **列出要重构的内容**
3. **重构后必须做回归测试**
